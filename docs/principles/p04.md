# Principle 4: The Effective Interface is Everything Observable

> **Canon (Esperanto)**:  
> *4. La efektiva interfaco estas ĉio observebla.  
> Ĉio, kion alia unuo povas observi, fariĝas dependeco, eĉ se neniu deklaris ĝin. Tial ŝanĝo de observebla konduto estas ŝanĝo de la pakto kaj tuŝas ĉiujn, kiuj dependas de ĝi.  
> Bazo: du sistemoj estas ekvivalentaj por observanto, se tiu ne povas distingi ilin; la efektiva interfaco estas la aro de ĉiuj observoj, kiu enhavas la deklaritan aron.  
> Signalo: ŝanĝo, kiun oni juĝis sendanĝera, rompas iun.*

---

## English Translation
Anything another unit can observe becomes a dependency, even if no one declared it. Therefore, a change in observable behavior is a change in the pact and affects everyone who depends on it.

- **Basis**: Two systems are equivalent to an observer if the observer cannot distinguish between them; the effective interface is the set of all observations, which subsumes the declared set.
- **Signal**: A change deemed harmless breaks someone else.

---

## Theoretical Grounding: Observational Equivalence and Hyrum's Law

In formal systems theory, two systems $S_1$ and $S_2$ are observationally equivalent to an observer $O$ if and only if for all observations $\omega \in \Omega$, $\omega(S_1) = \omega(S_2)$.

In software engineering, this reality is captured empirically by **Hyrum's Law**:
> *"With a sufficient number of users of an API, it does not matter what you promise on the contract: all observable behaviors of your system will be depended on by somebody."*

Whether an attribute was intentionally published in an OpenAPI specification or was merely an incidental side effect (e.g., response execution timing, JSON key ordering, error message phrasing, database row return sequence), if another system observes it, it becomes a structural dependency in $E_M$ and an implicit communication coupling in $E_C$.

---

## Operational Diagnostic: The Signal in Practice

- **Observable Signal**: An engineer merges an internal optimization or refactoring that ostensibly passes all provider unit tests, only to immediately receive outage alerts because a consumer service broke.
- **Structural Remedy**:
  - Treat all changes to observable output as potential breaking changes.
  - Implement consumer-driven contracts that explicitly capture and verify the exact subset of observable behaviors relied upon by each downstream consumer.
  - Apply proactive fuzzing and behavioral randomization (e.g., shuffling JSON keys, jittering response latencies) during testing to discourage consumers from depending on undeclared incidental properties.
